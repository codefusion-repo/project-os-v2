# PM Operations Catalog (Catálogo de Operaciones PM)

Este documento mapea cada operación pública a sus componentes canónicos del kernel
(`kernel/workflows.json`, `kernel/execution_modes.json`, `kernel/outputs.json`,
`kernel/evidence.json`) y a sus variables PM. Es a la vez una guía de selección
para el PM **y** una tabla de mapeo canónico: cada fila resuelve a ids reales del
kernel. Las superficies (browser chat, terminal agent, Humano PM, destinatario
externo) aparecen en las columnas de Superficie. Las variables son selectores de
contexto, nunca autorización; la autoridad de escritura proviene de aprobación PM
exacta más los gates del kernel.

## Cobertura de operaciones

El alcance original de operaciones enumeró 26 operaciones candidatas. La operación
ficticia de *setup de terminal agent* fue removida con autorización del PM (ver
nota abajo), dejando 25 operaciones públicas. Este catálogo contiene **25
templates** (`00`–`24`).

**Familias restauradas** (no fueron autorizadas para eliminarse; se restauraron
como templates PM-facing en español con nombres descriptivos):

- *Upgrade kernel adoption* → `templates/operations/23-actualizar-adopcion-de-kernel-en-target.md`.
  Cubre la actualización de un target ya adoptado a una versión de kernel más
  reciente, distinta de la verificación read-only de `03` y de la auditoría de
  drift de `14`.
- *GitHub release object* → `templates/operations/24-draftear-comando-crear-release-github.md`.
  Cubre la publicación de un objeto Release de GitHub (`gh release create`, notas
  + tag), distinta del tag de git simple de `13`.

**Cierre de PR/issue**: la operación `10` produce `output.pm_command_bundle` bajo
`workflow.review_before_close` por decisión del PM; el paquete común de cierre
(comentarios faltantes, mark-ready, merge, cierre, limpieza remota/local) es
drafteo PM-facing, no ejecución del agente. El Humano PM ejecuta el bundle.

**Nota de operaciones eliminadas**: la operación ficticia de setup de terminal agent
fue removida y su guía vive en `docs/GETTING_STARTED.md`. Los terminal agents se
ejecutan a través de route-prompts post-adopción; no existe una operación PM-facing
de "setup" del agente.
