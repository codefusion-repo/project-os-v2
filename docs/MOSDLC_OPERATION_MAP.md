# MOSDLC Operation Map (MOSDLC.0)

Este documento es el mapa canónico objetivo de **MOSDLC — Modern AI SDLC
Operations**: la clasificación completa de todas las operaciones PM-written del
comentario MOSDLC del roadmap `#274` más las operaciones recomendadas aceptadas,
antes de cualquier migración masiva de templates.

Decisiones PM que gobiernan este mapa:

- Ninguna operación PM-written se elimina. Toda aparente duplicación se
  clasifica como alias, replacement, variant, merge-candidate, split-candidate
  o referencia de compatibilidad, con su estrategia de preservación explícita.
- El objetivo es reescribir la capa de operaciones bajo un estándar MOSDLC
  consistente; el catálogo actual `00`–`37` sigue siendo el canónico vigente y
  sirve como inspiración, referencia de compatibilidad y fuente de reemplazo
  hasta que la migración se apruebe por issues separados.
- El crecimiento de operaciones no es crecimiento del kernel: las operaciones
  son superficies de activación PM-facing (templates, docs y tests) sobre el
  kernel compacto existente. La única excepción aprobada es la ejecución interna
  de despliegue local/staging (#376), que agregó ids de kernel mínimos con gap
  estricto probado y aprobación PM exacta.
- Las operaciones de despliegue por agente son internal-only para uso
  CodeFusion y deben removerse, ocultarse, deshabilitarse o convertirse antes
  de un release público de Project OS.

Este mapa es documentación durable: no guarda estado vivo (issues, PRs, ramas,
validaciones ni resultados) y **no otorga permiso** de escritura, merge,
cierre, release, settings ni despliegue (`boundary.output_not_permission`).
La autoridad viene solo de aprobación PM exacta más los gates resueltos del
kernel para la acción específica.

## Cómo leer el mapa

Cada fila usa esta forma:

- **ID**: identificador estable `MOS-<fase>.<n>` (o `MOS-R.<n>` para las
  recomendadas aceptadas), en el orden exacto del comentario MOSDLC.
- **Operación**: nombre corto propuesto (kebab-case).
- **Enunciado PM original**: redacción PM textual preservada sin cambios.
- **Descripción**: `Hace:` qué hace, `Para:` para qué sirve, `Cómo:` cómo
  funciona a alto nivel.
- **Superficie**: browser_chat, terminal_agent, human_pm o external_recipient
  (los destinatarios externos no son actores kernel).
- **Workflow / Mode / Output / Evidence**: ids probables del kernel actual.
- **Variables**: requeridas y opcionales específicas de la operación. Todas
  las operaciones PM-facing incluyen además `PM_FEEDBACK_HUMANO` y
  `PM_QUESTION_HUMANO` como contexto opcional que nunca autoriza nada.
- **Aprobación PM**: comportamiento de aprobación; `Sí (exacta …)` significa
  aprobación PM exacta separada para esa acción.
- **Conexiones**: `Prev:` operaciones previas conectadas, `Next:` siguientes
  seguras, `Rec:` siguiente recomendada.
- **Clasificación**: new, replacement, alias, variant, merge-candidate,
  split-candidate, old-compatibility-reference o accepted-recommended.
- **Mapa 00–37**: operación actual relacionada, si existe.
- **Exposición**: public-safe o internal-only.
- **Riesgo**: low, medium o high.
- **Kernel/Template**: `template:` new, reuse-NN (nueva con forma de NN) o
  exists-NN (el template NN ya implementa la operación); `kernel:` no-change o
  candidate (posible cambio de kernel, nunca aplicado aquí).
- **Postura**: `sec:` std o strict (redacción obligatoria), `env:` entorno de
  despliegue si aplica, `notes:` req si depende de `Project-specific notes`
  del adapter target, `pre-release:` convert si debe removerse, ocultarse,
  deshabilitarse o convertirse antes de un release público.

## Crecimiento de operaciones vs crecimiento del kernel

Las 121 operaciones de este mapa se resuelven con los workflows, modes,
outputs y evidence ids existentes del kernel; no se asume un workflow por
operación. La única excepción es la ejecución de despliegue por agente: la
decisión #376 aplicó workflow.deployment, mode.delegated_deploy_execution y
evidence.deployment_readiness para ejecución interna local y staging (MOS-5.11 y
MOS-5.13), con producción (MOS-5.15) fuera del alcance del agente y en manos del
Humano PM. Ver
[Candidatos de cambio de kernel](#candidatos-de-cambio-de-kernel-resueltos-en-376).
Agregar una operación MOSDLC significa agregar template, filas de docs y tests;
agregar ids de kernel siempre exige gap estricto probado y aprobación PM exacta
separada.

## Decisión deployment-by-agent (internal-only)

El despliegue por terminal agent queda representado en el mapa como capacidad
**internal-only** para uso privado CodeFusion. Estas operaciones deben
removerse, ocultarse, deshabilitarse o convertirse antes de un release público
(MOS-R.23); la columna Exposición marca cada fila afectada con
`pre-release:convert`.

Una operación de despliegue puede ser ejecutada por terminal agent solo cuando
se cumplen todas estas condiciones:

- el adapter del target contiene `Project-specific notes` estables con
  comandos de deploy/acceso o notas de entorno target-owned;
- la operación recibe aprobación PM exacta para ese target, entorno y acción;
- el terminal agent sigue el adapter target y los gates resueltos del kernel;
- no se imprime, pega, commitea, sube, resume, cita ni expone ningún valor
  secreto: nada de `.env`, `.env.*`, claves privadas, API tokens, secretos
  OAuth/cliente, database URLs, cookies, session tokens, JWTs, credenciales de
  producción, claves de proveedores de pago, claves SSH/GPG, secretos de CI ni
  valores con apariencia de secreto;
- no se ejecutan dumps amplios de entorno/config como `env`, `printenv`,
  `set`, dumps de config de frameworks ni dumps de contexto de secretos de CI,
  salvo diagnóstico redactado scoped por separado;
- el agente reporta solo rutas de archivo, nombres de variables, nombres de
  comandos, tipo de riesgo y estado de redacción, con valores siempre como
  `[REDACTED]`;
- modificar secret stores, rotar claves, cambiar credenciales de producción,
  editar secretos de despliegue, tocar settings de pago/auth de producción o
  cambiar settings de proveedores externos requiere aprobación PM exacta
  separada adicional.

Cuando cualquiera de esas condiciones falta, la operación de ejecución falla
cerrada y **el despliegue queda con el Humano PM**, guiado por el checklist
humano y el bundle de comandos drafteados. Producción queda con el Humano PM
por defecto incluso cuando la ejecución por agente es posible; la delegación de
producción exige decisión PM explícita adicional por despliegue. El mapa
distingue local/debug, staging y producción, drafteo de comandos, ejecución
por agente, checklist humano, verificación post-deploy (MOS-R.13) y rollback
(MOS-R.15, MOS-R.16). `TARGET_ENVIRONMENT` permite que una sola forma de
template cubra varios entornos (MOS-R.11, MOS-R.12) sin colapsar las
operaciones PM-facing por entorno (MOS-5.1 a MOS-5.15), que se mantienen
separadas porque hacen más claro el flujo del PM.

## Candidatos de cambio de kernel (resueltos en #376)

La decisión #376 (MOSDLC.6a) resolvió los tres candidatos de ejecución de
despliegue con aprobación PM exacta y gap estricto probado. `workflow.deployment`,
`mode.delegated_deploy_execution` y `evidence.deployment_readiness` se aplicaron
al kernel para ejecución interna local y staging por terminal agent (MOS-5.11 y
MOS-5.13), internal-only y nunca public-safe por defecto. Producción (MOS-5.15)
no se ejecuta por agente: queda con el Humano PM por defecto y su prerrequisito
nombrado es una ruta más estricta aprobada por separado. Los detalles viven en
`docs/decisions/0001-fase5-deploy-execution-fail-closed.md`. Cualquier id de
kernel adicional sigue requiriendo un issue separado con gap estricto probado y
aprobación PM exacta (`boundary.separate_pm_approval`).

| Candidato | Gap | Justificación | Decisión |
|---|---|---|---|
| `workflow.deployment` | Ejecución de despliegue por agente (MOS-5.11, MOS-5.13) | workflow.issue_implementation está orientado a escritura de repo, no a mutación de entornos; deploy execution necesita readiness, ejecución gated y verificación. | Aplicado en #376 para local/staging internal-only; producción queda con el Humano PM. |
| `mode.delegated_deploy_execution` | Ejecutar comandos de despliegue target-owned no es commit/push/PR | Un mode explícito hace el gate de aprobación exacta por target/entorno/acción auditable y write-capable terminal-only. | Aplicado en #376; nunca ejecuta producción por agente. |
| `evidence.deployment_readiness` | Evidencia de readiness de entorno previa a ejecutar | Gate explícito de readiness, comandos target-owned y secret-safety antes de ejecutar. | Aplicado en #376; falla cerrado a status.blocked cuando falta readiness, comandos target-owned o secret-safety. |
